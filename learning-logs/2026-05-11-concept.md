# Today's System Design Problem: Idempotent Payment Processing

## The Scenario (The "Brainer" Issue)

Aap ek payment gateway bana rahe ho (think Stripe / Razorpay). User "Pay Now" button dabata hai. Network slow hai, browser timeout ho jata hai. User dobara click karta hai. Phir karta hai. Backend ko 3 requests milti hain - sab ka **same transaction**.

Aur to aur, retry karne wala mobile client out-of-order packets bhej raha hai: pehle `REFUND` event, fir `CHARGE` event aa gaya (because mobile network reordered them).

**The Challenge**:
- User ko **ek hi baar** charge hona chahiye (no double charge).
- Refund agar charge se pehle aaya, to system ko intelligently wait/reject karna padega.
- Database mein race condition aaye to balance corrupt ho jayega.
- Frontend ko "loading" se "success"/"failure" smoothly switch karna chahiye - chahe network 3 baar timeout ho.

Agar naively likhoge: `SELECT balance -> UPDATE balance`, to do concurrent requests ek saath chal kar **double-spend** kar denge. Production mein yeh ek class-action lawsuit hai.

---

## Concept 1: Java Core - `ConcurrentHashMap.computeIfAbsent` for Idempotency Cache

**Concept**: In-memory idempotency cache using `ConcurrentHashMap<String, CompletableFuture<PaymentResult>>` with `computeIfAbsent`.

**Why it matters here**: Jab same idempotency key se 3 requests aati hain (thread A, B, C ek saath), hum chahte hain ki sirf **ek thread actual payment process kare**, baki dono uska result wait karke return karein. `computeIfAbsent` atomic hai - JVM guarantee karta hai ki same key ke liye compute function sirf ek baar chalega.

```java
private final ConcurrentHashMap<String, CompletableFuture<PaymentResult>> inFlight =
    new ConcurrentHashMap<>();

public PaymentResult process(String idempotencyKey, PaymentRequest req) {
    CompletableFuture<PaymentResult> future = inFlight.computeIfAbsent(
        idempotencyKey,
        k -> CompletableFuture.supplyAsync(() -> doActualCharge(req))
    );
    return future.join();
}
```

**Production tie-in**: Stripe ka `Idempotency-Key` header exactly isi pattern pe based hai. Uber rides, PayPal transactions - sab idempotency keys use karte hain.

**Memory trick**: "Ek key, ek charge" - `computeIfAbsent` is the bouncer at the club. Same ID? Same drink, no double pour.

## Concept 2: Spring Boot - Custom `@Idempotent` AOP Annotation + `@Transactional(SERIALIZABLE)`

**Concept**: Spring AOP se ek custom `@Idempotent` annotation banao jo idempotency key extract kare, DB mein check kare, aur duplicate request ko cached response return kare. Saath mein `@Transactional(isolation = SERIALIZABLE)` for the actual money movement.

**Why it matters here**: Business logic mein har jagah `if (alreadyProcessed) return cached;` likhna messy hai. AOP yeh cross-cutting concern handle karta hai. `REQUIRES_NEW` ensure karta hai ki idempotency audit row save ho chahe outer transaction fail ho.

**Code pattern**:
```java
@Target(METHOD) @Retention(RUNTIME)
public @interface Idempotent { String keyHeader() default "Idempotency-Key"; }

@Aspect @Component
public class IdempotencyAspect {
    @Around("@annotation(idempotent)")
    public Object guard(ProceedingJoinPoint pjp, Idempotent idempotent) throws Throwable {
        String key = RequestContext.header(idempotent.keyHeader());
        return idempotencyStore.findExisting(key)
            .orElseGet(() -> safeExecute(pjp, key));
    }
}

@RestController
class PaymentController {
    @PostMapping("/charge")
    @Idempotent
    @Transactional(isolation = Isolation.SERIALIZABLE)
    public PaymentResult charge(@RequestBody PaymentRequest req) { ... }
}
```

**Interview phrasing**: "In this scenario, I'd use Spring's AOP-driven custom annotation `@Idempotent` because duplicate-request handling is a cross-cutting concern - I don't want every controller method to manually re-check the idempotency store. Combined with `@Transactional(SERIALIZABLE)` for the money move and `REQUIRES_NEW` for the audit row, I get atomicity AND replay safety in one declarative stack."

## Concept 3: SQL - `SELECT ... FOR UPDATE` + `UNIQUE` Constraint on `idempotency_key`

**Concept**: Pessimistic row-level lock (`SELECT ... FOR UPDATE`) on the wallet row, plus a `UNIQUE` constraint on `payments(idempotency_key)` to make the database itself reject duplicates.

**Why it matters here**: Application-level cache miss ho sakta hai (server restart, multiple pods). DB-level unique constraint is the **last line of defense** - no matter how many app servers retry, the second INSERT will throw a constraint violation. Aur `FOR UPDATE` ensure karta hai ki two concurrent debit operations same wallet row pe serialize ho jayein.

**SQL Example**:
```sql
CREATE TABLE payments (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key VARCHAR(64) NOT NULL,
    user_id         BIGINT NOT NULL,
    amount_cents    BIGINT NOT NULL,
    status          VARCHAR(16) NOT NULL,
    created_at      TIMESTAMPTZ DEFAULT now(),
    CONSTRAINT uniq_idem UNIQUE (idempotency_key)
);

CREATE TABLE wallets (
    user_id       BIGINT PRIMARY KEY,
    balance_cents BIGINT NOT NULL CHECK (balance_cents >= 0),
    version       BIGINT NOT NULL DEFAULT 0
);

BEGIN;

-- Step 1: Lock the wallet row (blocks other concurrent debits)
SELECT balance_cents FROM wallets WHERE user_id = $1 FOR UPDATE;

-- Step 2: Try to insert the payment - UNIQUE constraint blocks duplicates
INSERT INTO payments (idempotency_key, user_id, amount_cents, status)
VALUES ($key, $user, $amount, 'PENDING')
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING id;

-- Step 3: Debit only if insert succeeded
UPDATE wallets
SET balance_cents = balance_cents - $amount, version = version + 1
WHERE user_id = $1 AND balance_cents >= $amount;

COMMIT;
```

**The gotcha**: Agar tum `READ COMMITTED` isolation pe ho aur `FOR UPDATE` skip kar do - to **lost update** problem aata hai. Both transactions read `balance = 100`, both subtract 60, both write `40` - actually 80 spend hua but DB mein 40 bacha. User ke paas free 60 rupees. Multiply by 10M users => company khatam.

## Concept 4: Angular/Frontend - RxJS `shareReplay` + Stable Idempotency Key + Optimistic UI

**Concept**: Generate idempotency key **once per user intent** (not per HTTP retry). Use RxJS `shareReplay(1)` so multiple subscribers to the same payment observable get the **same in-flight request**, not new ones. Show optimistic UI, rollback on error.

**Why it matters here**: User "Pay" 3 baar dabata hai - frontend ko 3 HTTP calls nahi karne chahiye. Ek hi key, ek hi pending observable. Plus, agar response slow ho, optimistic UI dikha do ("Payment Processing...") aur server confirm hone pe success/rollback dikhao.

**Code pattern**:
```typescript
@Injectable({ providedIn: 'root' })
export class PaymentService {
  private pending = new Map<string, Observable<PaymentResult>>();

  pay(req: PaymentRequest): Observable<PaymentResult> {
    const key = req.idempotencyKey ?? crypto.randomUUID();
    req.idempotencyKey = key;

    if (this.pending.has(key)) {
      return this.pending.get(key)!;
    }

    const obs$ = this.http.post<PaymentResult>('/api/charge', req, {
      headers: { 'Idempotency-Key': key }
    }).pipe(
      retry({ count: 3, delay: (_, i) => timer(Math.pow(2, i) * 500) }),
      finalize(() => this.pending.delete(key)),
      shareReplay(1)
    );
    this.pending.set(key, obs$);
    return obs$;
  }
}

// Component
onPayClick() {
  this.uiState = 'PROCESSING';
  this.wallet.balance -= this.amount; // optimistic
  this.paymentService.pay(this.req).subscribe({
    next: r => this.uiState = 'SUCCESS',
    error: e => {
      this.wallet.balance += this.amount; // rollback
      this.uiState = 'FAILED';
    }
  });
}
```

## The Complete Solution

**How these 4 concepts work together**:

Frontend Angular ek **stable idempotency key** generate karta hai (UUID, per user intent). User chahe 10 baar click kare, RxJS `shareReplay` ek hi HTTP request rakhta hai. Wo request `Idempotency-Key` header ke saath Spring Boot pe jati hai. Spring ka `@Idempotent` AOP aspect pehle check karta hai - agar payments table mein yeh key exist karti hai, cached response return. Agar nahi, Java ka `ConcurrentHashMap.computeIfAbsent` in-flight dedup karta hai for concurrent requests in the SAME JVM. Phir `@Transactional(SERIALIZABLE)` ke andar SQL `SELECT ... FOR UPDATE` wallet row lock karta hai, `INSERT ... ON CONFLICT DO NOTHING` DB-level dedup deta hai (multi-pod safe), aur `CHECK (balance >= 0)` constraint negative balance se bachata hai. Response wapas frontend ko aata hai - success ya rollback.

**The flow**:
1. **Angular** generates UUID, dedups via `shareReplay`, sends with `Idempotency-Key` header.
2. **Spring Boot** AOP intercepts via `@Idempotent`, opens `@Transactional(SERIALIZABLE)`.
3. **Java Core** uses `ConcurrentHashMap.computeIfAbsent` for same-JVM concurrent dedup.
4. **SQL** executes `FOR UPDATE` lock + `UNIQUE` constraint + `CHECK` constraint - DB rejects duplicates.
5. Response flows back - Angular updates state or rolls back optimistic UI.

**What breaks if you skip any layer**:
- **Skip frontend dedup**: Server gets 10 simultaneous requests; multi-pod scenario causes thundering herd.
- **Skip Spring `@Transactional`**: Partial writes - payment row saved but wallet not debited.
- **Skip Java concurrent map**: Two threads in same JVM both hit DB, one wins via UNIQUE constraint but you wasted a DB round-trip and got an ugly exception.
- **Skip SQL `UNIQUE` + `FOR UPDATE`**: **Double-charge in production** when two pods process the same retried request simultaneously.

## Interview Answer (45 seconds)

**Opening**: "This problem requires defense-in-depth across all four layers because no single layer can solve idempotency alone - app caches miss, networks retry, databases race."

**Key points in order**:
1. **Frontend** generates a stable UUID per user intent and dedups in-flight via RxJS `shareReplay`.
2. **Spring Boot** uses a custom `@Idempotent` AOP annotation + `@Transactional(SERIALIZABLE)` to declaratively guard the endpoint.
3. **SQL** has a `UNIQUE` constraint on `idempotency_key` plus `SELECT ... FOR UPDATE` on the wallet row - the database is the last line of defense.
4. **Java Core** uses `ConcurrentHashMap.computeIfAbsent` so same-JVM concurrent retries share one in-flight computation.

**Closing**: "By combining `computeIfAbsent` + `@Idempotent` AOP + `UNIQUE` constraint + RxJS `shareReplay`, we guarantee that no matter how many times the user retries or how the network reorders packets, exactly one charge happens."

## Follow-Up Questions (Be Ready)

1. **Trade-off**: "SERIALIZABLE isolation is expensive - what are you sacrificing for safety?"
   *Answer*: Throughput drops because of locking. Acceptable for payments (low TPS per wallet); not acceptable for high-fanout reads. Mitigate via wallet sharding.

2. **Scale**: "At 10x load (1M payments/sec), what breaks first?"
   *Answer*: DB row locks become a hotspot. Solution: shard by `user_id`, use event-sourcing/CQRS so writes go to an append-only log and a reducer materializes balance.

3. **Edge case**: "Network dies after DB commit but before HTTP response - what happens on retry?"
   *Answer*: Retry hits `@Idempotent`, finds existing row by key, returns cached response. User never knows there was a failure.

4. **Optimization**: "How would you reduce p99 latency?"
   *Answer*: Move idempotency check to Redis (faster than DB), use optimistic locking (`version` column with CAS) instead of pessimistic `FOR UPDATE` for low-contention wallets.

## What You Should Be Able to Explain

After this daily lesson, you should be able to answer:

1. **How would you prevent race conditions in this system?**
   Combination of `ConcurrentHashMap.computeIfAbsent` (in-JVM), `SELECT ... FOR UPDATE` (cross-pod), and `UNIQUE` constraint (last-line defense).

2. **Walk me through the transaction flow from frontend to database.**
   Angular UUID -> shareReplay -> HTTP with `Idempotency-Key` -> Spring `@Idempotent` AOP check -> `@Transactional(SERIALIZABLE)` -> Java dedup -> SQL `FOR UPDATE` -> `INSERT ON CONFLICT` -> UPDATE wallet -> COMMIT -> response -> Angular state update.

3. **What happens if this operation fails halfway? How do you recover?**
   `@Transactional` rolls back the wallet update. Idempotency row may or may not be present. Client retries with same key - server returns cached failure response (if recorded) or re-attempts safely.

4. **How does `ConcurrentHashMap.computeIfAbsent` work with Spring's `@Transactional`?**
   The map dedups concurrent in-JVM requests BEFORE the transaction opens, reducing DB pressure. Each unique key gets its own transaction; duplicates wait on the same `CompletableFuture`.

5. **Why is `SERIALIZABLE` isolation necessary here?**
   Lower isolation levels (READ COMMITTED, REPEATABLE READ) allow phantom reads and lost updates on the wallet balance. SERIALIZABLE guarantees the read-modify-write on `balance_cents` is conflict-free.
