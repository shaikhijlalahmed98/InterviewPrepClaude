# Day 2 — 2026-05-12

# 🎯 Today's System Design Problem: Flash Sale Inventory — Stop Overselling at 100K RPS

## The Scenario (The "Brainer" Issue)

iPhone 17 launch din: 1000 units stock hai. 100,000 users ek saath "Buy Now" dabate hain in 2 seconds. Backend pe 8 servers running. Naive code:

```java
// THE BUG MOST DEVS WRITE
if (product.getStock() > 0) {
    product.setStock(product.getStock() - 1);
    repository.save(product);
}
```

**Result**: 1000 stock se 5,000 orders confirmed ho jate hain. Customer complaints, refunds, brand damage. Yeh classic **race condition + lost update** problem hai.

**The Challenge**:
- 8 backend instances → in-memory `synchronized` useless (sirf ek JVM tak)
- DB pe 100K concurrent reads → "stock > 0" check sab ke liye `true` return karega
- Optimistic retries → thundering herd, p99 latency 5s+ blow up
- User UX → "Sold Out" instantly dikhana hai, na ki order place hone ke baad

> **This is different from Day 1's idempotency problem.** Idempotency = "same request multiple times". Oversell = "different requests racing for shared resource". Both need defense-in-depth, but the locks live in different places.

## Concept 1: Java Core — `Semaphore` + `AtomicInteger` (CAS, Lock-Free)

**Concept**: `java.util.concurrent.Semaphore` for **admission control**, plus `AtomicInteger.compareAndSet` for **lock-free** in-JVM counters.

**Why it matters here**: Per-JVM bottleneck — agar ek instance ko 100K/8 = 12,500 requests milte hain ek saath, tum 12,500 threads ko DB tak nahi jaane de sakte. Semaphore `tryAcquire(timeout)` se 99% ko upfront reject karo (fail-fast in <50ms). AtomicInteger CAS se metrics counter race-free update hoti hai bina `synchronized` block ke (lock-free = no thread parking).

```java
// Per-JVM admission gate
private final Semaphore admissionGate = new Semaphore(200);  // max 200 in-flight per JVM
private final AtomicInteger inFlight = new AtomicInteger(0);

public OrderResult tryReserve(Long pid, Long uid) {
    if (!admissionGate.tryAcquire(50, TimeUnit.MILLISECONDS)) {
        throw new TooManyRequestsException("Server busy, retry");
    }
    inFlight.incrementAndGet();
    try {
        return doReserveWithDistributedLock(pid, uid);
    } finally {
        inFlight.decrementAndGet();
        admissionGate.release();
    }
}
```

**Production tie-in**: Amazon Lightning Deals — frontend pe "you're in queue" message? Wo Semaphore-style admission control hi hai. Netflix Hystrix bulkhead pattern same idea use karta hai. Resilience4j ka `Bulkhead.ofDefaults()` literally Semaphore wraps karta hai.

**Memory trick**: **"Semaphore = club ka bouncer"** — capacity full, line mein wait karo ya rejected. **AtomicInteger = lock-free counter, no thread sleeps**.

## Concept 2: Spring Boot — Redisson Distributed Lock + `@Transactional(REPEATABLE_READ)`

**Concept**: Redis-based distributed lock (`RLock` from Redisson) + `@Transactional(isolation = REPEATABLE_READ, timeout = 2)`.

**Why it matters here**: 8 servers ke beech coordination chahiye. JVM-level Semaphore sirf ek instance pe kaam karta hai — server A aur server B dono apne-apne Semaphore acquire kar lenge same product ke liye. Redisson distributed lock ek **single source of truth** deta hai with **fencing token** (Redlock algorithm) — koi bhi ek server lock hold karega, baki wait karenge ya timeout pe fail karenge.

`@Transactional(REPEATABLE_READ)` ensure karta hai ki transaction ke andar tum jo `stock` value pehli baar padhi, wo dobara consistent rahe (no phantom reads). SERIALIZABLE bhi chal jaye but throughput half ho jaye.

**Code pattern**:
```java
@Service
public class InventoryService {

    @Autowired private RedissonClient redisson;
    @Autowired private InventoryRepository repo;
    @Autowired private OrderService orderService;

    @Transactional(isolation = Isolation.REPEATABLE_READ, timeout = 2)
    public OrderResult reserve(Long productId, Long userId, String idempotencyKey) {
        RLock lock = redisson.getLock("inv:lock:" + productId);
        boolean acquired = false;
        try {
            // wait up to 200ms, hold up to 1500ms (auto-release if JVM dies)
            acquired = lock.tryLock(200, 1500, TimeUnit.MILLISECONDS);
            if (!acquired) throw new TooManyRequestsException("Try again");

            int rows = repo.atomicDecrement(productId);   // SQL atomic UPDATE
            if (rows == 0) throw new OutOfStockException();

            return orderService.create(productId, userId, idempotencyKey);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}
```

**Interview phrasing**: "In this scenario, I'd use Redisson's `RLock` with a lease timeout because in-JVM `synchronized` doesn't span the 8-server cluster, and Spring's `@Transactional` alone can't coordinate across nodes — only the database row lock or a distributed lock can. The lease timeout protects against JVM crash leaving the lock held forever."

## Concept 3: SQL — Atomic `UPDATE ... WHERE stock > 0` + `CHECK` Constraint

**Concept**: Single-statement atomic decrement with predicate + table-level `CHECK (stock >= 0)` as the **immutable last line of defense**.

**Why it matters here**: Distributed lock fail ho sakta hai (Redis network split, GC pause, leased lock expiry mid-transaction). Database **must not** allow stock to go negative under any circumstance. Atomic UPDATE acts as a single CAS operation — either it decrements (returns `1`) or fails (returns `0`). CHECK constraint is the immutable guard that throws even if your code is buggy.

**SQL Example**:
```sql
-- Schema with the immutable invariant
CREATE TABLE inventory (
    product_id BIGINT PRIMARY KEY,
    stock      INT NOT NULL CHECK (stock >= 0),
    version    BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- The ONLY safe decrement (atomic, no read-then-write)
UPDATE inventory
SET    stock     = stock - 1,
       version   = version + 1,
       updated_at = NOW()
WHERE  product_id = :pid
  AND  stock > 0;
-- If 0 rows updated → out of stock. No race possible because
-- the predicate evaluation + write happen under the same row lock.

-- Audit + idempotency for reservations (Day 1 lesson reused)
CREATE TABLE reservation (
    id              UUID PRIMARY KEY,
    product_id      BIGINT NOT NULL REFERENCES inventory(product_id),
    user_id         BIGINT NOT NULL,
    idempotency_key VARCHAR(64) NOT NULL UNIQUE,   -- dedup
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

INSERT INTO reservation (id, product_id, user_id, idempotency_key)
VALUES (:rid, :pid, :uid, :key)
ON CONFLICT (idempotency_key) DO NOTHING;
```

**The gotcha**: Agar tum `SELECT stock FROM inventory WHERE id=?` karke phir Java mein check karke `UPDATE` karoge — even with `@Transactional(READ_COMMITTED)` — tum **lost-update bug** khaoge. Two transactions read `stock=1`, both compute `stock-1=0`, both save `0` — but **two orders** confirm. Use the **single atomic UPDATE** or `SELECT ... FOR UPDATE`. CHECK constraint = "even if my application code is buggy, DB will throw `ConstraintViolationException` and rollback."

## Concept 4: Angular — `BehaviorSubject` + `exhaustMap` + Optimistic UI + WebSocket Backpressure

**Concept**: `BehaviorSubject<number>` for live stock, `exhaustMap` to ignore button-mash retries, optimistic decrement with rollback on 4xx, WebSocket subscription with `throttleTime` for backpressure.

**Why it matters here**: User experience MUST NOT show "Available" when stock is 0 globally. Server pushes live stock via WebSocket — but at 100K events/sec, naive `subscribe` will freeze the browser tab. `throttleTime(500)` ensures UI updates max 2x/sec. `exhaustMap` on click handler prevents button-mash flood (`switchMap` would cancel in-flight, `mergeMap` would parallelize — both wrong here). Optimistic UI shows "Reserved!" instantly, rolls back if server returns 409.

**Code pattern**:
```typescript
@Injectable({ providedIn: 'root' })
export class FlashSaleService {
  private stock$ = new BehaviorSubject<number>(0);
  private click$ = new Subject<void>();

  // Live stock from WebSocket, throttled to avoid render thrashing at 100K eps
  stockUpdates$ = this.ws.connect('/topic/stock/iphone17').pipe(
    throttleTime(500, undefined, { leading: true, trailing: true }),
    tap(s => this.stock$.next(s)),
    shareReplay(1)
  );

  // Click handler: ignore extra clicks while one is in-flight (NOT switchMap)
  buy$ = this.click$.pipe(
    exhaustMap(() => {
      const prev = this.stock$.value;
      this.stock$.next(prev - 1);                       // optimistic decrement

      return this.http.post<Order>('/api/reserve', {
        productId: 'iphone17',
        userId: this.auth.userId,
        idempotencyKey: crypto.randomUUID()             // Day 1 dedup
      }).pipe(
        catchError(err => {
          this.stock$.next(prev);                       // ROLLBACK optimistic
          this.toast.error(err.status === 409
            ? 'Sold out!' : 'Try again');
          return EMPTY;
        })
      );
    })
  );

  click() { this.click$.next(); }
}
```

## 🧠 The Complete Solution

**How these 4 concepts work together**:

1. **Angular** generates idempotency UUID, `exhaustMap` blocks duplicate clicks, optimistic UI gives instant feedback, WebSocket throttles live stock updates so browser doesn't freeze.
2. **Spring Boot** receives request → Redisson distributed lock acquired (timeout 200ms, lease 1.5s) → `@Transactional(REPEATABLE_READ)` opens.
3. **Java Core** Semaphore at the JVM admission layer rejects 99% of overflow before lock attempt. AtomicInteger lock-free counters for live metrics.
4. **SQL** atomic `UPDATE ... WHERE stock > 0` either succeeds (1 row) or fails (0 rows). `CHECK (stock >= 0)` is the **immutable contract** the DB itself enforces.

**The flow** (single user click):
```
Angular click → exhaustMap (drop dupes) → POST /reserve (UUID, optimistic UI -1)
         ↓
Spring controller → @Transactional(REPEATABLE_READ) opens
         ↓
Java Semaphore.tryAcquire(50ms) — fail fast if JVM overloaded
         ↓
Redisson.tryLock("inv:lock:pid", 200ms, 1500ms) — cluster coordination
         ↓
SQL: UPDATE inventory SET stock=stock-1 WHERE id=? AND stock>0
         ↓
Rows == 1 → INSERT order, COMMIT, return 201
Rows == 0 → ROLLBACK, return 409 OutOfStock
         ↓
Angular: 201 → confirm UI; 409 → rollback BehaviorSubject + show "Sold Out"
```

**What breaks if you skip any layer**:
- **Skip Java Semaphore** → 8 servers × 12.5K threads = 100K DB connections requested → connection pool exhausted → cascading failure across all services sharing that DB.
- **Skip Spring Redisson lock** → 8 servers race on same row → DB row-lock queue 5K deep → p99 latency 5s+ → users see spinner forever.
- **Skip SQL atomic UPDATE / CHECK** → Read-modify-write in Java = lost update = oversell. Missing CHECK = silent negative stock when application has bug.
- **Skip Angular `exhaustMap` + optimistic rollback** → User mashes Buy 20× → 20 reservation attempts → even with idempotency, UX shows wrong stock count and stale state.

## 🎬 Interview Answer (45 seconds)

**Opening**: "Flash sale oversell is fundamentally a race-condition problem at every layer — frontend, application server, and database. The defense must be layered because no single layer can solve it alone."

**Key points**:
1. **Frontend (Angular)**: `exhaustMap` to ignore duplicate clicks, idempotency UUID per intent, optimistic UI with rollback on 409, WebSocket with `throttleTime` for live stock.
2. **Spring Boot**: Redisson distributed lock spans the cluster (8 servers); `@Transactional(REPEATABLE_READ)` for snapshot consistency within the transaction.
3. **SQL**: Single atomic `UPDATE ... WHERE stock > 0` — no read-then-write. `CHECK (stock >= 0)` is the immutable last guard that the DB itself enforces.
4. **Java Core**: `Semaphore` admission control rejects overflow in <50ms before DB sees it. `AtomicInteger` lock-free counters for live metrics.

**Closing**: "Combining Java Semaphore + Spring's Redisson distributed lock + SQL's atomic UPDATE with CHECK constraint + Angular's `exhaustMap` with optimistic rollback ensures **exactly the available stock is sold, no more, no matter how many concurrent users hit Buy Now**."

## 📊 Follow-Up Questions (Be Ready)

1. **Trade-off**: "Distributed lock = extra Redis hop = +5ms p50 latency. Worth it?" → Yes, alternative is heavy DB row-lock contention which is worse at scale. For simpler systems, you can skip the lock entirely and rely only on the SQL atomic UPDATE — it's race-safe by itself, the lock is for *throughput shaping*.
2. **Scale**: "What at 1M RPS?" → Pre-warm Redis with stock counter, use Lua script in Redis to atomic decrement (skip DB on hot path), reconcile to SQL async via outbox pattern. This is exactly what Flipkart Big Billion Days uses.
3. **Edge case**: "Network fails after DB commit, before client gets response?" → Idempotency key dedup (Day 1's lesson) — client retries with same UUID, server returns existing reservation row from `reservation` table.
4. **Optimization**: "How to cut p99?" → Move admission to API gateway (Envoy rate limit), shard DB by `product_id`, CDN-cache "sold out" page so worker tier never sees those requests.
5. **Failure mode**: "Redisson leased lock expires before SQL commits — what happens?" → Two servers might both have the "lock". But SQL atomic UPDATE + CHECK is the safety net — only one decrement succeeds, the other gets 0 rows and 409s. Lock is for performance, DB is for correctness.

## 🎯 What You Should Be Able to Explain

1. "Why can't we just use `synchronized` in Java for this?" → It's per-JVM; doesn't span the 8-server cluster.
2. "Walk me through the transaction flow from click to confirm." → See the connection map above.
3. "What happens if Redis dies mid-transaction?" → DB CHECK + atomic UPDATE saves you. Lock degrades to DB row-lock contention (slower but correct).
4. "How does `Semaphore` differ from `RateLimiter` here?" → Semaphore = concurrent in-flight count cap; RateLimiter = requests per time window. We use Semaphore because we care about *parallelism*, not rate.
5. "Why `REPEATABLE_READ` and not `SERIALIZABLE`?" → SERIALIZABLE serializes transactions = throughput halved. The atomic single-statement UPDATE is consistent on its own; REPEATABLE_READ gives us snapshot consistency for the order-creation that follows in the same tx.
